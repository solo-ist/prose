    connection's token), and name-only `find` searches for `*prose*` and `mcp*.json`.

### Networking

- **Docker Desktop, not podman.** Both clients run under Docker Desktop 29.6.1. The podman machine is stopped, and
  `host.containers.internal` doesn't resolve.
- **The loopback bind is enough.** Docker Desktop forwards `host.docker.internal` to the Mac's loopback interface. A
  test server bound only to `127.0.0.1:9898` answered both containers. It saw the peer as `127.0.0.1`, with
  `Host: host.docker.internal:9898`.
  - Prose's bind address needs no change.
  - M1's Host allowlist entry for `host.docker.internal` is what lets the request in, and the connection's bearer token
    is what gates it.
- **Every loopback port is reachable from these containers.** Any container on an ordinary (non-internal) Docker
  Desktop network can reach any loopback port on the Mac. Here that means Open WebUI and both LibreChat stacks. The
  ports include unauthenticated ones, such as an Electron debug port: `PROSE_DEBUG_PORT`, or the dev window's 9222.
  - The harness agent lanes sit only on `internal: true` networks, which have no gateway, so they don't get this
    route.
  - This isn't a Prose bug, but it's worth knowing before leaving a debug port open while such containers run.

**Configuration.** The entry went into the rendered `librechat.yaml`. That file is the co-op's `librechat.yaml` merged
with `chat/local.yaml`, at container start. The tracked `chat/` files weren't edited. Instead, a compose override:

  `mcpSettings`);
- set the token as `PROSE_QA_TOKEN` in the container's environment when it started.

```yaml
mcpServers:
  prose:
    type: streamable-http
    url: http://host.docker.internal:9898/mcp
    headers:
      Authorization: "Bearer ${PROSE_QA_TOKEN}"   # the LibreChat QA token, from the container's env (redacted)
    timeout: 60000
    requiresOAuth: false                          # attempt 2; see #1278
mcpSettings:
  allowedAddresses:
    - "host.docker.internal:9898"                 # SSRF protection stays on; only this host:port is exempt
```

**Attempt 1, without `requiresOAuth`: ❌ (#1278).**
1. LibreChat probed the URL without the configured header.
2. Prose answered `401` with `WWW-Authenticate: Bearer realm="Prose"`.
3. LibreChat therefore marked `prose` as `OAuth Required: true`, loaded no tools at startup, and sent every call into an
   OAuth flow that failed. The model got "OAuth authentication required".

Prose's own LibreChat snippet (Settings → Integrations) has this problem and an earlier one:
- its bare `allowedAddresses: - host.docker.internal` fails LibreChat 0.8.8's config schema, which requires
  `host:port`;
- an invalid config stops LibreChat at startup.

The first connection was revoked and replaced for attempt 2.

### Notes

- **No client name beside the label, for either client.** This is by design, not a finding.
  - Both clients speak protocol `2025-11-25`, which carries `clientInfo` only in `initialize`.
  - Prose's HTTP endpoint is stateless, so a `tools/call` arrives without it (`clientInfoOf` in
    `src/shared/mcp/server.ts`).
  - The records show the connection label, which is the identity. Claude Code showed `· claude-code` in run 1 because
    it sends `clientInfo` with every request.
- **LibreChat doesn't pass Prose's MCP `instructions` to the model** unless the server sets
  `serverInstructions: true`. Its log says `Server Instructions: N/A`. The loop worked without them, with explicit
  prompts. #1278 suggests adding the setting to the snippet.
- **After a revoke, Open WebUI shows no error in API-driven chats.** The failure goes out as a socket event, and the
  model simply answers without tools. That is client behaviour.
- **#1266** is still open, although its fix (#1269) merged into `release/v1.9.1`. GitHub closes issues only on
  merges into the default branch. Step 7 passes in both clients on `84dcc27`.
