**Side incident, about the run itself (not Prose).** In the first attempt the model had no MCP tools, so it
explored the machine with 96 shell commands.
- **Local only.** The model was `qwen3-coder` through the local gateway at `127.0.0.1:4000`, which routes to the
  llama-server on `:8082`. Every route in the gateway's config is local, and telemetry is off, so nothing it read left
  the machine.
- **Sandboxed.** Codex ran with `sandbox_mode = "read-only"` and `approval_policy = "never"`:
  - its `curl` calls to Prose and to the app's debug port were refused ("operation not permitted");
  - it asked for escalation twice and was rejected both times;
  - no write outside the scratch directory traces to it.
- **What it read.**
  - The scratch run files, including the file holding the two QA connection tokens. It also put one token into a
    `curl` command that the sandbox blocked.
  - Outside the scratch directory: `which`, `ps`, `lsof`, `netstat`, `env | grep -i mcp` (which showed only that
    connection's token), and name-only `find` searches for `*prose*` and `mcp*.json`.
  - Nothing in `~/.ssh`, the keychain, 1Password, `.env` files, `~/.codex` or `~/.claude`.
- **Contained.** Both connections were revoked during the run (HTTP 401 verified), and Prose recorded no call from
  them (the target document has no comments, suggestions or events).
- **Evidence.** Codex's own `--json` event log was deleted at cleanup, before it was asked to be kept. Its stderr and
  the command listings recovered from the session transcript are kept outside the repo.
- **Lesson for future runs:** an agent with shell access can read any file this user can, so keep tokens only in the
  client's environment.

  affected, and the installed app's `~/Library/Application Support/Prose/prose.sock` is far shorter.
